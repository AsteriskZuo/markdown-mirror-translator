# 模型使用建议

本项目是一款 VS Code 插件，用于翻译 Markdown 文档，并以双栏形式对比显示原文和译文。

这份文档用于帮助后续开发时判断：哪些任务值得使用推理能力更强但成本更高的模型，哪些任务可以切换到性价比更高的模型。

## 推荐分工

在早期设计、架构规划、复杂多文件实现阶段，优先使用 GPT-5.5 high。

在主体架构稳定后，处理范围明确的小功能、小修复、小调整时，优先使用 GPT-5.4 high。

简单判断标准是：如果任务需要决定系统结构、协调多个模块、保证长期可维护性，就用 GPT-5.5 high。如果任务已经定义清楚，改动范围局部，预期文件也比较明确，就用 GPT-5.4 high。

## 适合使用 GPT-5.5 High 的任务

- 设计插件整体架构和模块边界。
- 设计从 Markdown 输入到译文输出的核心翻译流程。
- 设计双栏 Webview 的交互、状态同步和显示策略。
- 定义翻译服务提供方抽象、配置项结构和错误处理方式。
- 规划 Markdown 解析、分段、缓存、增量翻译和重试机制。
- 实现第一版端到端主流程，包括插件命令、服务层、Webview 和测试。
- 排查跨多个模块的问题，尤其是需要多轮定位和修复的复杂 bug。
- 当现有结构阻碍后续功能时，重构核心抽象。

GPT-5.5 high 的价值主要体现在：需要高质量推理、持续使用工具、跨多个文件保持一致设计思路的场景。

## 适合使用 GPT-5.4 High 的任务

- 修复某个明确的命令注册问题。
- 调整 Webview 布局、样式或文案。
- 新增或重命名一个配置项。
- 优化某个单独的 Markdown 解析或分段函数。
- 为已有行为补充聚焦的单元测试。
- 更新 README、CHANGELOG、插件市场文案或使用示例。
- 根据明确的 TypeScript、lint、打包错误进行修复。
- 在架构已经明确后，做小范围行为调整。

当一个任务可以用一两句话说清楚，并且基本能预判会修改哪些文件时，GPT-5.4 high 通常是更合适的默认选择。

## 本项目的重点判断

对这个插件来说，高成本推理能力最值得投入在以下决策上：

- Markdown 如何解析，以及如何切分成适合翻译的片段。
- 译文片段如何映射回原始 Markdown 文档。
- Webview 中原文栏和译文栏如何保持滚动、定位和状态同步。
- 翻译服务提供方如何与 VS Code 插件代码解耦。
- 失败、取消、限流、部分结果等状态如何表示。
- 如何设计缓存，避免重复翻译浪费 API 调用。
- 如何在不依赖真实翻译服务的情况下编写测试。

当这些核心决策已经写入文档并完成基础实现后，日常开发应优先使用 GPT-5.4 high。只有当任务重新跨越这些边界时，再切回 GPT-5.5 high。

## 升级回 GPT-5.5 High 的规则

维护阶段默认从 GPT-5.4 high 开始。如果出现以下情况，再切换回 GPT-5.5 high：

- 修复会影响多个模块，而且正确的模块边界还不清楚。
- 需要一次性理解并修改很多文件。
- 某个 bug 已经经过一两轮聚焦修复但仍未解决。
- 改动会影响翻译正确性、缓存策略或 Webview 同步逻辑。
- 任务本质上是在重设抽象，而不是修改某个实现细节。

这样可以在控制成本的同时，把更强的推理能力用在真正会影响结果质量的地方。
